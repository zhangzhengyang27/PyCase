# PyCase 数据契约 v2 设计稿（B1 对稿物）

> 状态：待对稿（2026-09-29）｜ 上位文档：[重设计方案](redesign-plan.md) §5（D9 强制条件）｜ 基线提交：d463d8a
> 本文冻结 B2/B3 的数据层：集合文件格式、派生索引、物化缓存、迁移工具与数据访问协议（G7 在此定稿，B2 落地）。
> 对稿通过前不写实现；对稿通过后，B2 按本文实现，护栏按 §7 映射再表达。

## 0. 一句话方案

真相源仍是可 diff 的集合 JSON（**只增加 `schema_version` 与校验规则，不搬家**）；「加载」不再写盘——
启动只解析 JSON 建索引（本机实测 10ms）+ 读构建期烘焙的派生事实（省 ≈1.7s 重算）；
示例代码在运行/编辑/AI/上传真正需要时才物化进**版本化缓存**（当前首次全量物化的 108MB 写盘从启动路径消失）；
缓存带清单、有上限、可清理、可自愈；任何格式变更必须过迁移工具（dry-run / 备份 / 逐条校验 / 回滚）。

## 1. 现状实测（2026-09-29，本机 macOS arm64，1496 条 / 14 集合）

| 组件 | 实测 | 备注 |
|---|---|---|
| 解析全部集合 JSON | **0.010s** | 启动真正必需的成本 |
| `load()`（缓存已热） | 0.26–0.51s | 含 1496 次 .py 改写 + 31 个目录指纹比对——纯为物化付的费 |
| `load()`（缓存冷，全量物化） | 0.44s / 1426 目录 / **108MB** | 首次启动的写盘量；`list_examples` 每次都要求它完成 |
| 派生事实全量（parse 0.12 + quality 0.75 + risk 0.60 + imports 0.24） | **≈1.7s** | 首次 `list_examples` 的序列化成本，每次进程启动重付 |
| `list_examples` RPC（生产路径，热） | 1.71s / 响应 **3.44MB** | 响应去掉 `code` 后 0.96MB（-72%） |
| 物化缓存现状 | 3151 目录 / 118MB，**1725（55%）为陈旧项** | 示例改名/删除后从未清理（如 `topics_turtle-burst-v16…v27`） |

数据集事实：101 条带 `dir`（落在 31 个目录，最多 16 条共享一个目录）；979 条带 `requirements`；1426 条有 `title`；
id 全局无重复；22 条 id 含中文/空格等需安全化的字符（`sciviz_examples.json` 自动生成批次）；3 个集合缺顶层 `name`。

关于 C2 的「17s」：那是冒烟环境端到端观测（[ROADMAP](../ROADMAP.md) P1②，沙箱 I/O 争用 + 后台 venv 引导并行）。
本机分解显示服务端组件合计 ≈2s（见上表）——**结论方向不变**：启动路径不应含物化与全量重算，且缓存治理缺陷（55% 陈旧）与耗时无关、独立成立。

## 2. 集合文件 v2

### 2.1 Schema（增量）

```json
{
  "schema_version": 2,
  "name": "基础示例集",
  "description": "可选的集合说明",
  "examples": [
    {
      "id": "hello_world",
      "name": "hello.py",
      "title": "打招呼",
      "category": "topics",
      "tags": ["基础"],
      "description": "打印问候语",
      "requirements": ["requests"],
      "dir": "topics/.../code",
      "code": "print('Hello')\n"
    }
  ]
}
```

v1 → v2 的全部差异：**新增顶层 `schema_version`（整数）+ 明确校验规则**。字段语义、编码（UTF-8）、
写盘风格（`ensure_ascii=False, indent=2`、tmp + `os.replace` 原子替换）均不变。
未知字段一律**保留不丢弃**（旧字段、未来字段都不炸）；`save_item` 回写时保留顶层未知键（现有行为）。

### 2.2 校验与规范化（load 期）

| 规则 | 违规处置 | 现状数据 |
|---|---|---|
| `schema_version` 缺失 = v1（只读兼容，见 §2.3） | 记警告 | 全部 14 个 |
| `id` 非空、全局唯一 | 跨集合重复：保首个并记警告（不静默） | 0 处 |
| `id` 字符集干净（`[A-Za-z0-9._-]`） | **不判错**（改名=破坏收藏/历史身份），记警告 | 22 条 |
| `name` 非空、无路径分隔符、`.py` 规范化 | 拒绝该条（跳过并计入校验报告） | 0 处 |
| `code` 非空字符串 | 拒绝该条 | 0 处 |
| `dir` 相对根且在根内 | 拒绝该条（越界即数据外泄通道，沿用现防护） | 0 处 |
| `requirements` 合法包名 | 丢弃非法项并记警告 | 0 处 |
| 顶层 `name` 必填（v2） | 迁移补齐（回退 stem）；load 期回退 stem 不报错 | 3 个集合 |

校验产物是一份**机器可读的校验报告**（条数、逐项原因），load 不因校验失败整体罢工（fail-visible 而非 fail-crash）；
迁移工具则以严格模式运行——**报告非空即拒写**。

### 2.3 版本策略与兼容窗口

- v2 应用读 v1 集合（写时升级），兼容窗口 = 一个版本周期（v1.0.x），M6 后收口为硬失败。
- v1 应用读 v2 集合：v2 只增字段，旧代码忽略 `schema_version` 继续可用——**双向兼容**是本次设计的硬约束。
- 冻结的 `scripts/`（17 个工具读写集合）继续产出 v1 形状文件，属兼容范围，**不重写**。
- `user_examples/` 与内置同构：导入器写 `schema_version: 2`；旧用户集合在运行时被**自动迁移**（见 §6）。

## 3. 派生数据：索引与事实

### 3.1 启动路径（无写盘）

```
解析 14 个集合 JSON（10ms） → 建树 + 扁平索引（id → item，元数据 + code 在内存）
                          ↘ 载入派生事实索引（§3.2）→ 校验集合哈希
耗时目标：< 50ms（不含 venv 引导，venv 引导仍在后台线程）
```

`item.path` 变为**计划路径**（由 §4.2 的命名规则确定性推导，尚未落盘）——渲染层对它的使用仅为展示（实测：
除一条系统消息外无逻辑依赖），语义变化安全。

### 3.2 烘焙索引（派生事实，可弃可重建）

派生事实 = 质量分、HIGH 风险明细、静态状态（broken/empty/ok）、第三方 import 清单、code 哈希。
它们是**只依赖 code 的确定性函数**，因此构建期烘焙、随包分发：

- 位置：打包版随应用分发（只读）；开发/失配时重建并写缓存根。单一路径读取。
- 头部：`schema_version`、facts 规则版本（评分/安全规则变更即改版）、集合内容哈希、生成时间。
- 命中：集合哈希逐一比对（1.9MB 哈希 ≈ 10ms）→ 直接用；缺失/失配 → 全量重算一次（≈1.7s）并缓存。
- `run_status` 的缺依赖维度依赖运行环境（venv 模块索引），**不烘焙**：运行时以「静态事实 + 模块索引」廉价合成
  （实测带模块索引全量 0.73s，且可在 venv 就绪后就地重算）。
- 应用内编辑保存 → 该集合标记脏，下次启动重建；运行中的内存事实即时失效（现有行为）。

### 3.3 事实分层

| 层 | 内容 | 生命周期 |
|---|---|---|
| 真相源 | 集合 JSON 的人写字段 | 永久（git 追溯） |
| 烘焙事实 | quality / risk / 静态状态 / imports / code 哈希 | 可弃，构建期或首次失配时生成 |
| 运行时事实 | run_status（合成缺依赖）、收藏/历史（已在主进程存储） | 内存/会话 |
| 物化缓存 | 可运行的真实文件（§4） | 可弃，按需生成 |

## 4. 物化与缓存治理

### 4.1 按需物化（新契约核心 API）

`ensure_materialized(item) -> Path | None`——幂等，**唯一**的落盘入口；
运行、编辑保存、资源上传/列举、AI 解释、评分实跑一律先经它。
load 不再物化；缓存缺失/损坏时由它自愈重建（G1 的自愈语义保留）。

### 4.2 缓存布局与命名

```
<可写根>/.json_examples_cache/v2/            ← 版本化根（v1 旧根保留原位、可清理、不自动删）
    <safe_name>/                              ← 示例工作目录（含物化基线 + 用户资产）
        .manifest.json                         ← 清单：契约版本、base_key、基线文件列表、last_used
        <name>.py + 基线文件 + 用户上传资源
```

命名规则：`safe_name = sanitize(id 或 dir)`；**有损替换（发生字符替换）时追加 `-<sha256(raw)[:8]>`**——
按构造即无碰撞、跨会话稳定；干净键保持原名（现数据集中 1404 条 id 干净、31 个 dir 有损）。

### 4.3 基线刷新与用户资产

- `base_key = sha256(源目录指纹 + code + 合并后 requirements)`（单文件示例为 `sha256(code + requirements)`）。
- 清单命中且 base_key 一致 → 仅确保目标 `.py` 与 JSON 逐字节一致（不一致才写）；不一致 → 刷新基线：
  按清单**删除旧基线文件、拷入新基线文件**，随后重写清单并记录 `last_used`。
- **用户资产与运行产物（不在基线清单中的文件）在刷新中永不被删**——修掉现状缺陷（目录型示例源一变整目录重建，
  上传资源连带丢失）。
- 陈旧兄弟文件必须随基线刷新移除（否则会"跑的是旧兄弟模块"）——靠清单做差集。

### 4.4 清理、上限与自愈

- 自愈：目录/清单缺失 ⇒ 重建（G1 用例覆盖）；`.py` 被外力改坏 ⇒ 下次 `ensure_materialized` 覆盖回 JSON 内容。
- 上限：默认 **1GiB**，超限按 `last_used` LRU 淘汰；含用户资产的条目仅在无干净候选时才被淘汰，淘汰有日志。
- 手动清理（A6 设置入口）：默认只清「干净」条目（保留含用户资产的），另有显式「全部清理」；
  同时列出 v1 旧根占用（1725 个陈旧目录，55%）供一键回收。
- 孤儿清扫：不在当前索引键集合中的条目在启动后后台缓慢回收（不阻塞、不静默删用户资产）。

## 5. 数据访问协议（G7 设计：本轮定稿，B2 落地）

| RPC | v1（现状） | v2 |
|---|---|---|
| `list_examples` | 全量 1496 条**含 code**（3.44MB） | **只发索引**：元数据 + 派生徽章 + 计划路径，不含 `code`（实测 0.96MB，-72%） |
| `get_example` | 单条含 code | 不变（编辑器/AI/详情的取码路径） |
| 代码搜索 | 前端在本地全量 code 上搜 | 新增服务端 `search_examples(query)`：sidecar 内存中检索（名称/标签/描述/code），返回 id + 命中原因；前端防抖调用 |
| 运行/保存/资源/AI | 按 id | 不变（按 id，不传路径）；落盘前隐含 `ensure_materialized` |

其余方法（`run_example`/`save_example`/导入/删除等）签名不变；完整方法表在 B2 落地时补齐金标（G7）。
上传资源与运行产物所在目录 = §4.2 的工作目录。

## 6. 迁移工具（B2 落地）

构成：**运行库**（落位 app 内，供 sidecar 自动迁移用户集合）+ **薄 CLI**（同库入口，dry-run / apply / verify / rollback 子命令）。

- `--dry-run`：扫描内置 + 用户集合，输出逐文件变更计划 + 校验报告（非空即拒写），不落盘。
- `apply`：逐文件 **先备份**（各自目录下 `.backup/<ts>/`，含哈希清单 + gitignore 条目）再原子写 v2；
  只做 §2.1 的增量变更；user 侧 id 冲突才改名（沿用 `_2` 后缀口径），内置 id **永不改**（收藏/历史身份）。
- `verify`：**逐条语义等价断言**——条数、id 集合、`code` 逐字节、各元数据字段逐一相等，1496/1496 通过才算过；
  apply 后自动复验（重读全量再断言），不过即报错并提示回滚。
- `--rollback <ts>`：按备份清单逐文件还原并复验；运行侧另有只读兼容兜底（v1 文件直接可读，§2.3）。
- **演练纪律**：apply 前必须先在**完整副本**（集合 + user_examples + 缓存）上跑通 dry-run → apply → verify → rollback
  全链路；该演练固化为 G8 护栏测试，作为切换真相源的放行条件。

## 7. 护栏映射与再表达（对稿项）

「何时物化」是本次重设计要改的**实现时序**，不是行为契约；「物化结果、自愈、同步、原子、三态」才是契约。
G1 的断言点从「`load()` 后」移到「`ensure_materialized()` 后」，断言事实逐条不变：

| 护栏 | v1 断言点 | v2 断言点 | 断言事实（不变） |
|---|---|---|---|
| G1 金标 | load 后 | load + ensure_materialized 后 | 14 集合 / 1496 条；索引完整；.py 与 JSON 逐字节一致 |
| G1 目录型 | load 后 | ensure_materialized 后 | 兄弟文件随目录到位；run_pythonpath 语义不变 |
| G1 自愈 / 同步 | 两次 load | 两次 ensure_materialized | 删缓存可重建；源变（含"缓存比源新"反例）必重拷 |
| G2 原子写 | 不变 | 不变 | 写失败不损坏集合、无 .tmp 残留 |
| G3 三态 / 不 fail-open | 不变（2 条 xfail 不动） | 不变 | 五态判定与高危明细同源 |
| G6 用户集合 | 导入/删除/去重 | 不变 + 删除后缓存条目同步清理 | 跨集合去重、原子写回 |
| G7 协议金标 | 无 | 新增（§5，B2 绿） | 全方法契约 |
| G8 迁移 | 无 | 新增（§6，B1 设计/B2 绿） | 逐条等价 + 回滚演练 |

护栏再表达与契约同 PR 评审；禁止借"重设计"之名放宽任何断言事实。

## 8. 禁止项与验收

禁止：无迁移工具的破坏性格式变更；未演练的切换；测试写真相源；自动删除用户数据（v1 旧缓存只标记/手动回收）；
绕过 `ensure_materialized` 直接按路径读缓存；内置集合 id 改名。

验收（B2 门禁）：G1–G8 全绿（含再表达后的 G1、新增 G7/G8）；冷启动到 `list_examples` 索引就绪 < 50ms（不含 venv）；
启动路径零物化写盘（用例断言缓存根在 load 后无新文件）；缓存上限/清理/孤儿回收各有用例；
迁移工具在副本上跑通 dry-run → apply → verify → rollback 全链路。

## 9. 待拍板决策点

1. **内容载体**：保持 JSON 内联 code（推荐）／外移真实 .py 源码树／SQLite。
2. **派生事实交付**：构建期烘焙 + 启动哈希校验（推荐）／纯内存每次重算／生成物提交进 git。
3. **资产保全**：基线与用户资产分离、刷新不删资产（推荐）／维持现状同目录重建。
4. **缓存上限**：1GiB + LRU + 手动清理（推荐）／512MB／只手动清理不设上限。

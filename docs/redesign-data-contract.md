> 状态：已对稿（2026-09-29，4 项决策见 §9）｜ 上位文档：[重设计方案](redesign-plan.md) §5（D9 强制条件）｜ 基线提交：d463d8a
> 本文冻结 B2/B3 的数据层：真相源形态、派生索引、运行工作区、迁移工具与数据访问协议（G7 在此定稿，B2 落地）。

## 0. 一句话方案

**示例的代码外移为真实 `.py` 源码树**（git 追踪、外部工具链可直接跑、可 diff 可 review）；集合 JSON 退化为**元数据清单**
（id/展示名/标签/依赖 → 文件路径），不再内联 code。「加载」只读清单（本机实测解析 10ms）+
构建期烘焙的派生事实（省 ≈1.7s 重算）；运行/上传/产物落在**版本化工作区**（基线拷贝 + 用户资产分离，1GiB LRU）；
任何格式变更必须过迁移工具（dry-run / 备份 / 逐条校验 / 回滚），1496 条逐字节等价是切换放行条件。

## 1. 现状实测（2026-09-29，本机 macOS arm64，1496 条 / 14 集合）

| 组件 | 实测 | 备注 |
|---|---|---|
| 解析全部集合 JSON | **0.010s** | 启动真正必需的成本（v2 后清单更小） |
| `load()`（缓存已热） | 0.26–0.51s | 含 1496 次 .py 改写 + 31 个目录指纹比对——纯为物化付的费 |

| 派生事实全量（parse 0.12 + quality 0.75 + risk 0.60 + imports 0.24） | **≈1.7s** | 首次 `list_examples` 的序列化成本，每次进程启动重付 |
| `list_examples` RPC（生产路径，热） | 1.71s / 响应 **3.44MB** | 响应去掉 `code` 后 0.96MB（-72%） |
| 物化缓存现状 | 3151 目录 / 118MB，**1725（55%）为陈旧项** | 示例改名/删除后从未清理（如 `topics_turtle-burst-v16…v27`） |

0 条内容不同、31 条目标文件在源目录缺失**（notebook 章节 1–4 的 code 只在 JSON 里）；979 条带 `requirements`；
1426 条有 `title`；id 全局无重复；22 条 id 含中文/空格等需安全化字符（`sciviz_examples.json` 自动生成批次）；

关于 C2 的「17s」：那是冒烟环境端到端观测（[ROADMAP](../ROADMAP.md) P1②，沙箱 I/O 争用 + 后台 venv 引导并行）。
本机分解显示服务端组件合计 ≈2s（见上表）——**结论方向不变**：启动路径不应含物化与全量重算，且缓存治理缺陷（55% 陈旧）与耗时无关、独立成立。

## 2. 真相源 v2：清单 JSON + 真实源码树

### 2.1 布局（内置与用户同构）

```
json_examples/                    ← 内置集合根
  bulk_basics.json                ← 清单：只存元数据
  bulk_basics/                    ← 迁移外移出的真实源码（单文件示例 = 一文件一示例）
    hello_world.py
  …（其余集合同理）
topics/…  tools/…  projects/…  examples_assets/…
                                  ← 既有真实目录：101 条 dir 型示例的源码与数据兄弟保持原位，
                                    file 指向原路径（保留出处，不搬家、不复制）
userData/user_examples/           ← 用户集合根（与内置同构）
  <集合>.json
  <集合>/<文件>.py                 ← 导入即拷贝真实文件（原始字节，不再 JSON 转义）
```

`file` 字段 = **相对清单所在目录**的路径：新外移文件写 `<集合>/<name>`；原位示例写 `../topics/…` 形态（仅 101 条，由迁移工具生成，人几乎不手写）。

### 2.2 清单 schema

```json
{
  "schema_version": 2,
  "name": "基础示例集",
  "description": "可选的集合说明",
  "examples": [
    {
      "id": "hello_world",
      "name": "hello.py",
      "title": "打招呼",
      "category": "topics",
      "tags": ["基础"],
      "description": "打印问候语",
      "requirements": ["requests"],
      "file": "bulk_basics/hello_world.py"
    }
  ]
}
```

v1 → v2 的差异：顶层加 `schema_version`；条目加 `file`、**删除 `code`**；`dir` 退役（= `file` 的父目录，兄弟文件天然在位）。
`id` 仍是身份（收藏/历史/协议键），`name` 仍是展示文件名；未知字段保留不丢弃。写盘沿用原子纪律（tmp + `os.replace`）。
`requirements` 留在清单（是元数据），供运行时装包与构建期汇总依赖清单。

### 2.3 校验与规范化（load 期）

| 规则 | 违规处置 | 现状数据 |
|---|---|---|
| `schema_version` 缺失 = v1（只读兼容，见 §2.4） | 记警告 + 提示迁移 | 全部 14 个 |
| `id` 非空、全局唯一 | 跨集合重复：保首个并记警告（不静默） | 0 处 |
| `id` 字符集干净（`[A-Za-z0-9._-]`） | 不判错（改名=破坏身份），记警告 | 22 条 |
| `name` 非空、无路径分隔符、`.py` 规范化 | 拒绝该条（跳过并计入校验报告） | 0 处 |
| **`file` 存在、非空、解析后仍在集合根内**（越界即数据外泄通道，沿用现防护） | 拒绝该条 | 迁移产物 |
| `requirements` 合法包名 | 丢弃非法项并记警告 | 0 处 |
| 顶层 `name` 必填（v2） | 迁移补齐（回退 stem）；load 期回退 stem 不报错 | 3 个集合 |

校验产物是一份**机器可读的校验报告**；load 不因校验失败整体罢工（fail-visible 而非 fail-crash）；
迁移工具以严格模式运行——**报告非空即拒写**。

### 2.4 版本策略与兼容窗口

- v2 应用读 v1 清单（`code` 内联）：兼容窗口 = 一个版本周期（v1.0.x），只读可用；M6 后收口为硬失败。
- v1 应用读 v2 清单：`code` 缺失会跳过条目——**v1 应用不可读 v2 清单**，这是单向破坏，由迁移工具的备份 + 回滚兜底（§6）。
- 冻结的 `scripts/`（17 个工具读写集合）在迁移后**退役不再运行**：生成器类归档；仍被构建链依赖的等价能力由 B2 提供
  最小替代（依赖汇总：只读各清单的 `requirements`，等价产出仓库根 `requirements.txt`）。
- `user_examples/` 与内置同构；旧用户集合在运行时被**自动迁移**（§6，含备份）。

## 3. 派生数据：索引与事实

### 3.1 启动路径（无写盘）

```
读 14 个清单（元数据）→ 建树 + 扁平索引（id → item：元数据 + file 计划路径）
                      ↘ 载入派生事实索引（§3.2）→ 校验清单与文件哈希
耗时目标：< 50ms（不含 venv 引导，venv 引导仍在后台线程；文件内容哈希实测成本 B2 记录，超预算降级为 size+mtime 快路径）
```

`item.path` 变为**计划路径**（= 真实文件路径；运行仍走工作区，§4）。

### 3.2 烘焙索引（派生事实，可弃可重建）

派生事实 = 质量分、HIGH 风险明细、静态状态（broken/empty/ok）、第三方 import 清单、每文件内容哈希。
它们是**只依赖文件内容的确定性函数**，因此构建期烘焙、随包分发：

- 位置：打包版随应用分发（只读）；开发/失配时重建并写缓存根。单一路径读取。
- 头部：清单 schema 版本、facts 规则版本（评分/安全规则变更即改版）、清单哈希 + 逐文件内容哈希、生成时间。
- 命中：哈希逐一比对 → 直接用；缺失/失配 → 全量重算一次（≈1.7s）并缓存。
- `run_status` 的缺依赖维度依赖运行环境（venv 模块索引），**不烘焙**：运行时以「静态事实 + 模块索引」廉价合成
  （实测带模块索引全量 0.73s）。
- 应用内编辑保存 → 重写真实文件 + 该示例事实即时失效 + 该集合标记脏，下次启动重建。

### 3.3 事实分层

| 层 | 内容 | 生命周期 |
|---|---|---|
| 真相源 | 清单 JSON + 真实 .py 源码树（git 追踪） | 永久 |
| 烘焙事实 | quality / risk / 静态状态 / imports / 内容哈希 | 可弃，构建期或首次失配时生成 |
| 运行时事实 | run_status（合成缺依赖）、收藏/历史（主进程存储，按 id） | 内存/会话 |
| 运行工作区 | 基线拷贝 + 用户资产 + 运行产物（§4） | 可弃（资产除外，见 §4.3） |

## 4. 运行工作区与缓存治理

### 4.1 按需工作区（新契约核心 API）

`ensure_workspace(item) -> Path | None`——幂等，**唯一**的落盘入口；
运行、资源上传/列举、AI 实跑一律先经它（编辑直接写真实文件；安全扫描/评分直接读真实文件，不需工作区）。
load 不建工作区；工作区缺失/损坏时由它自愈重建。单文件与目录型示例统一走工作区（运行产物与源码树隔离，git 不脏）。

### 4.2 工作区布局与命名

```
<可写根>/.json_examples_cache/v2/            ← 版本化根（v1 旧根保留原位、可清理、不自动删）
    <safe_name>/                              ← 示例工作区
        .manifest.json                         ← 清单：契约版本、base_key、基线文件列表、last_used
        <name>.py + 基线兄弟文件 + 用户上传资源 + 运行产物
```

命名规则：`safe_name = sanitize(id)`（目录型示例按 `file` 的集合内相对路径）；**有损替换时追加 `-<sha256(raw)[:8]>`**——
按构造即无碰撞、跨会话稳定；干净键保持原名。

### 4.3 基线刷新与用户资产

- `base_key = sha256(目标文件内容 + 兄弟目录指纹（若有） + 合并后 requirements)`。
- 清单命中且 base_key 一致 → 仅确保工作区目标 `.py` 与真实文件逐字节一致（不一致才写）；不一致 → 刷新基线：
  按清单**删除旧基线文件、拷入新基线文件**，随后重写清单并记录 `last_used`。
- **用户资产与运行产物（不在基线清单中的文件）在刷新中永不被删**——修掉现状缺陷（目录型示例源一变整目录重建，
  上传资源连带丢失）。
- 陈旧兄弟文件必须随基线刷新移除（否则会"跑的是旧兄弟模块"）——靠清单做差集。

### 4.4 清理、上限与自愈

- 自愈：工作区/清单缺失 ⇒ 重建；`.py` 被外力改坏 ⇒ 下次 `ensure_workspace` 覆盖回真实文件内容。
- 上限：默认 **1GiB**，超限按 `last_used` LRU 淘汰；含用户资产的条目仅在无干净候选时才被淘汰，淘汰有日志。
- 手动清理（A6 设置入口）：默认只清「干净」条目（保留含用户资产的），另有显式「全部清理」；
  同时列出 v1 旧根占用（1725 个陈旧目录，55%）供一键回收。
- 孤儿清扫：不在当前索引键集合中的条目在启动后后台缓慢回收（不阻塞、不静默删用户资产）。

## 5. 数据访问协议（G7 设计：本轮定稿，B2 落地）

| RPC | v1（现状） | v2 |
|---|---|---|
| `list_examples` | 全量 1496 条**含 code**（3.44MB） | **只发索引**：元数据 + 派生徽章 + 真实文件路径，不含 `code`（实测 0.96MB，-72%） |
| `get_example` | 单条含 code | 不变（编辑器/AI/详情的取码路径，服务端按需读真实文件） |
| 代码搜索 | 前端在本地全量 code 上搜 | 新增服务端 `search_examples(query)`：元数据内存检索 + **code 按需读文件**，返回 id + 命中原因；前端防抖调用 |
| 运行/保存/资源/AI | 按 id | 不变（按 id，不传路径）；运行时隐含 `ensure_workspace`，保存写真实文件（原子替换） |

其余方法（`run_example`/`save_example`/导入/删除等）签名不变；完整方法表在 B2 落地时补齐金标（G7）。
上传资源与运行产物所在目录 = §4.2 的工作区；用户示例删除 = 清单条目 + 真实文件 + 工作区三处同步清理。

## 6. 迁移工具（B2 落地）

构成：**运行库**（落位 app 内，供 sidecar 自动迁移用户集合）+ **薄 CLI**（同库入口，dry-run / apply / verify / rollback 子命令）。

### 6.1 变更计划（按现状数据逐类处理）

| 类 | 现状 | 迁移动作 |
|---|---|---|
| 单文件示例（1395 条） | code 内联 | 写真实文件到 `<集合根>/<集合>/<name>`；清单换 `file`、删 `code` |
| 目录型·文件已在位（70 条） | code 与源文件逐字节一致 | **不写文件**（零内容改动）；清单指向原位 `../…` |
| 目录型·目标文件缺失（31 条） | code 只在 JSON | 把 code 落成真实文件写入该源目录（数据兄弟天然在位）；清单指向原位 |
| 顶层缺 `name`（3 个集合） | — | 补齐（回退 stem） |
| 用户集合 | 与内置同构，含内联 code | 同规则迁移到用户集合根；id 冲突沿用 `_2` 后缀口径，**内置 id 永不改**（收藏/历史身份） |

### 6.2 四步流程与纪律

- `--dry-run`：扫描内置 + 用户集合，输出逐文件变更计划 + 校验报告（非空即拒写），不落盘。
- `apply`：逐文件**先备份**（各自集合根下 `.backup/<ts>/`，含哈希清单；.gitignore 增补该目录）再原子写；
  只做 §6.1 的变更，不触示例内容语义。
- `verify`：**逐条语义等价断言**——条数、id 集合、`code`↔`file` 内容**逐字节**、各元数据字段逐一相等，1496/1496 通过才算过；
  apply 后自动复验（重读全量再断言），不过即报错并提示回滚。**通过前不得把 v2 清单/源码树用于任何发布。**
- `--rollback <ts>`：按备份清单还原清单文件并**删除迁移新建的源码文件**（还原到 v1 状态）；再跑 `verify` 的等价断言（v1 侧）。
- **演练纪律**：apply 前必须先在**完整副本**（集合 + user_examples + 缓存）上跑通 dry-run → apply → verify → rollback
  全链路；该演练固化为 G8 护栏测试，作为切换真相源的放行条件。

## 7. 护栏映射与再表达（对稿项）

「何时/如何物化」是本次重设计要改的**实现时序**，不是行为契约；「内容等价、自愈、同步、原子、三态」才是契约。
再表达后的映射：

| 护栏 | v1 断言点 | v2 断言点 | 断言事实（不变） |
|---|---|---|---|
| G1 金标 | load 后物化 | 清单 + 真实树直接断言 | 14 集合 / 1496 条；`file` 全部存在；内容哈希与烘焙索引一致 |
| G1 目录型 | load 后兄弟文件 | ensure_workspace 后 | 兄弟文件随工作区到位；run_pythonpath 语义不变 |
| G1 自愈 / 同步 | 两次 load | 两次 ensure_workspace / 改真实文件后 | 删工作区可重建；真实文件变（含"工作区比源新"反例）必刷新 |
| G2 原子写 | 清单写回 | 清单 + **编辑真实文件** + 导入拷贝 | 写失败不损坏文件、无 .tmp 残留 |
| G3 三态 / 不 fail-open | 不变（2 条 xfail 不动） | 不变（读真实文件） | 五态判定与高危明细同源 |
| G6 用户集合 | 导入/删除/去重 | 不变 + 文件/工作区同步清理 | 跨集合去重、原子写回 |
| G7 协议金标 | 无 | 新增（§5，B2 绿） | 全方法契约 |
| G8 迁移 | 无 | 新增（§6，B1 设计/B2 绿） | 逐条等价 + 回滚演练 |

护栏再表达与契约同 PR 评审；禁止借"重设计"之名放宽任何断言事实。

## 8. 禁止项与验收

禁止：无迁移工具的破坏性格式变更；未演练的切换；测试写真相源；自动删除用户数据（v1 旧缓存与旧清单只标记/手动回收）；
绕过 `ensure_workspace` 直接按路径写工作区；内置集合 id 改名；迁移中改动示例代码语义（含空白与注释）。

验收（B2 门禁）：G1–G8 全绿（含再表达后的 G1、新增 G7/G8）；冷启动到 `list_examples` 索引就绪 < 50ms（不含 venv）；
启动路径零写盘（用例断言缓存根在 load 后无新文件）；工作区上限/清理/孤儿回收/资产保全各有用例；
迁移工具在副本上跑通 dry-run → apply → verify → rollback 全链路，1496/1496 逐字节等价。

## 9. 对稿记录（2026-09-29 已拍板）

1. **内容载体 = 外移为真实 .py 源码树**（清单 JSON 只存元数据；既有 101 条原位保留出处）。
2. **派生事实 = 构建期烘焙 + 启动哈希校验**；开发/失配自动重建。
3. **资产保全 = 基线与用户资产分离**；工作区刷新不删用户资产与运行产物。
4. **缓存上限 = 1GiB + LRU + 手动清理**（含 v1 旧根回收入口）。

由此确立的硬约束：v1 应用不可读 v2 清单（单向破坏）——由迁移备份/回滚与"逐条校验通过才放行"兜底；
`scripts/` 生成器类脚本退役，依赖汇总由 B2 提供只读清单的最小替代。

  与 B1 审计分类逐一对应；`--apply` 通过**逐条复验**（条数、id 集合、`code`↔真实文件逐字节、元数据字段）；
  `--verify` 独立复验通过。备份留在 `json_examples/.backup/<ts>/`（已 gitignore，可 `--rollback`）；
- 迁移后形态：`json_examples/` 下每个集合一个同名目录，真实源码树就位 + 14 个只存元数据的清单；`examples_assets/` 下补写 31 个目录型缺档文件。

### 10.2 烘焙事实索引（§3.2，已落地）

- 产物：`json_examples/facts.json`（1496 条 · 14 清单哈希 · 488KB），构建期由 `python -m app.facts_cli bake` 生成，随包分发；
- 头部：清单 schema 版本 + **facts 规则版本**（评分/安全/静态/主题谓词任一变更即失效）+ 生成时间；
  逐条存 `sha256/size/file` 与派生事实（`imports/deps/quality/risk_*/static/theme`）；
- 命中与失配：load 时**逐文件哈希**校验，命中即用（实测 1496 个文件全量哈希 ≈ 15ms）；
  失配**逐条**复用命中项、只重算变化项（与全量重算逐字段等价，由 `test_g1_facts_reuse_equals_full_rebuild` 钉住），
  并把结果写入缓存根 `…/.json_examples_cache/v2/facts.json`，下次启动即命中；
- `run_status` 的缺依赖维度不烘焙：运行时 = 静态事实 + 模块索引合成（优先级与 `compute_run_status` 一致）；
- 冷启动实测：索引就绪 **43–46ms**（预算 50ms；其中哈希校验 15ms、清单解析 6ms、条目构建约 20ms）；
  启动路径零写盘（命中随包烘焙时，用例断言缓存根在 load 后无新文件）。

### 10.3 依赖清单最小替代（scripts 退役）
